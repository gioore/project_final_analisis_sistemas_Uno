2.4 Reglas de negocio

  • Multitenancy: Cada paciente pertenece exclusivamente a un tenant. Todos los queries de base de datos filtran por tenant_id obtenido de la cabecera X-Tenant-ID.
  • Unicidad del expediente: El número de expediente debe ser único dentro del mismo tenant. Se valida tanto en creación como en actualización.
  • Autenticación requerida: Todas las rutas API del módulo requieren un token JWT válido y la cabecera X-Tenant-ID.
  • Autorización por roles: El backend está preparado con Spatie Permission para restringir operaciones según el rol (Admin = CRUD completo, Recepcionista = CRUD sin eliminar, Médico = solo lectura).
  • Validación de integridad: No se permite registrar pacientes con fecha de nacimiento futura.

4. Explicación de los cambios realizados

4.1 Capa de Base de Datos

Se creó la migración 2026_06_13_000001_create_pacientes_table.php que define la tabla pacientes con 13 columnas de datos más las columnas de timestamps. La tabla incluye una clave foránea tenant_id que referencia a tenants.id con borrado en cascada, y una restricción única compuesta por (tenant_id, numero_expediente) para garantizar la unicidad del número de expediente dentro de cada tenant.

Se implementó el modelo Eloquent Paciente en app/Models/Paciente.php con:

  • Atributo $fillable con todos los campos asignables masivamente.
  • Cast de fecha_nacimiento a tipo date.
  • Relación belongsTo(Tenant::class) para acceso al tenant padre.
  • Uso del trait HasFactory para pruebas y seeders.

Se creó la factory PacienteFactory que genera datos de prueba realistas utilizando FakerPHP, con valores aleatorios para nombres, fechas, géneros, tipos de sangre, etc.

El seeder PacienteSeeder crea 20 pacientes de muestra asociados al primer tenant registrado en el sistema.

Archivos creados:

  • database/factories/PacienteFactory.php
  • database/seeders/PacienteSeeder.php

Archivos modificados: database/seeders/DatabaseSeeder.php (se agregó la llamada a PacienteSeeder).

4.2 Capa de Backend (API)

Se implementó el controlador PacienteController en app/Http/Controllers/Api/V1/PacienteController.php con cinco métodos que conforman el CRUD completo:

MétodoEndpointDescripción
index()GET /api/v1/pacientesRetorna el listado de pacientes del tenant actual, con soporte para búsqueda por texto (nombre, apellido, expediente, teléfono) y filtro por género.
store()POST /api/v1/pacientesCrea un nuevo paciente con validación completa de campos y verificación de unicidad del número de expediente.
show()GET /api/v1/pacientes/{id}Retorna el detalle de un paciente específico, scoped al tenant.
update()PUT /api/v1/pacientes/{id}Actualiza los datos de un paciente. Valida unicidad del expediente excluyendo el registro actual.
destroy()DELETE /api/v1/pacientes/{id}Elimina un paciente del sistema.

Todos los métodos:

  • Obtienen el tenant actual desde $request->attributes->get('tenant') (inyectado por TenantMiddleware).
  • Filtran todos los queries por tenant_id para garantizar el aislamiento multi-tenant.
  • Retornan respuestas JSON con código HTTP adecuado (200, 201, 404, 422).
  • Incluyen mensajes de error descriptivos en español.

Las rutas se registraron en routes/api.php usando Route::apiResource('/pacientes', PacienteController::class) dentro del grupo de middleware ['tenant', 'jwt.auth'], lo que asegura que todas las operaciones requieran autenticación JWT y selección de tenant.

Archivos creados:

  • app/Http/Controllers/Api/V1/PacienteController.php

Archivos modificados: routes/api.php.

4.3 Capa de Frontend (Vue 3)

Se implementó el frontend del módulo siguiendo los patrones existentes en el proyecto (Composition API con <script setup>, Pinia para estado, Vue Router para navegación, Axios para peticiones HTTP y Tailwind CSS para estilos).

Store Pinia

Se creó el store stores/paciente.js con estado reactivo (pacientes, currentPaciente, loading) y cinco acciones asíncronas: fetchAll, fetchById, create, update, delete. Cada acción maneja la comunicación con la API a través de Axios.

Componentes reutilizables

  • PacienteTable.vue: Tabla genérica que recibe un arreglo de pacientes y renderiza filas con columnas de expediente, nombre, apellido, teléfono, género y acciones (Ver, Editar, Eliminar). Emite evento @delete para la eliminación.
  • PacienteForm.vue: Formulario reutilizable que funciona tanto para creación como para edición. Recibe como prop un objeto paciente en modo edición. Incluye validaciones visuales de campos, manejo de errores del servidor y estados de carga. Organizado en secciones (datos personales, contacto, emergencia).

Páginas

  • PacienteListPage.vue: Página principal del módulo. Muestra el listado con búsqueda en tiempo real (debounce 400ms), filtro por género, botón para nuevo paciente, estados de carga, vacío y error, y modal de confirmación para eliminación.
  • PacienteCreatePage.vue: Página que renderiza el formulario en modo creación. Al enviar, llama a store.create() y redirige al listado.
  • PacienteEditPage.vue: Página que carga los datos del paciente por ID y renderiza el formulario en modo edición. Muestra estado de carga mientras obtiene los datos.
  • PacienteShowPage.vue: Vista de detalle con información organizada en cuatro tarjetas: información personal, contacto, contacto de emergencia y alergias conocidas.
